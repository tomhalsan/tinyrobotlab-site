Runtime Mechanics

How Tiny Robot Works

Every task submitted to the platform moves through an explicit, visible state machine rather than an undocumented prompt chain. Here is how capability discovery, availability evaluation, and evidence-conditioned research operate step by step.

Step-by-Step Flow

1. Capability-Driven Task Dispatch

In static systems, tasks are dumped into hardcoded worker queues. Tiny Robot Lab replaces static queues with dynamic candidate discovery and runtime availability checks.

The 7-Stage Dispatch Lifecycle

2 Determine Capability

3 Candidate Discovery

4 Availability Check

5 Deterministic Routing
→
6 Target Dispatch
→

  1. Prompt Input: An operator submits a natural-language task prompt via the Prototype Console or HTTP API.
  2. Capability Determination: The platform analyzes task intent and classifies the required capability (e.g., general or research).
  3. Candidate Discovery: The orchestrator queries registered agents to find all instances advertising support for the required capability.
  4. Availability Evaluation: Registered candidates are evaluated against liveness policies using heartbeat timestamps and execution state (distinguishing ready, busy, stale, and offline).
  5. Deterministic Routing: An eligible candidate is selected deterministically and an audit record of the routing decision is preserved.
  6. Target Dispatch: The task is dispatched to the chosen agent's dynamically advertised delivery target, with no assumed queue topology.
  7. Execution & Result: The agent consumes the task, emits operational state transitions over Redis, and records the final output.

Specialist Agent

2. Grounded Research Execution Pipeline

When a task requires research, asking an LLM to search and summarize in a single prompt invites hallucinations and opaque failures. The Research Agent breaks execution into discrete, observable stages.

Multi-Stage Evidence Pipeline

Research Agent
1 Public Web Retrieval
→
2 Candidate Evidence
→
3 Quality Evaluation
→
4 Conditioned Synthesis
→
5 Attributed Findings

How evidence is evaluated and retained:

  • Retrieval: The research query is sent to a web retrieval adapter (e.g., Tavily), returning raw search snippets and candidate URLs.
  • Candidate Evidence Normalization: Each snippet is structured with its source URL, page title, textual snippet, and provider relevance indicators.
  • Deterministic Evidence Evaluation: Before any generative LLM is invoked, pure Python domain logic scores evidence-ranking signals: domain authority tiers, topical keyword density, content length, and snippet freshness. Weak or irrelevant items are discarded.
  • Conditioned Synthesis: The inference model receives strictly the retained evidence items and is instructed to synthesize findings based exclusively on those sources.
  • Attributed Findings: The synthesized response includes structured source citations, allowing learners and operators to inspect which evidence drove each finding.
⚠️ Important Distinction: Evaluated Evidence vs. Factual Truth
  • Evaluated evidence is not "verified proof." Our EvidenceEvaluator applies heuristic ranking signals (domain tier, keyword overlap, content length) to filter noise. It does not possess mathematical proof of factual accuracy.
  • Cross-domain keyword overlap is not semantic corroboration. Two independent websites sharing similar vocabulary may simply be repeating the same press release or common phrasing.
  • Retrieval quality is bounded by the provider. If the upstream retrieval API returns low-quality or irrelevant candidates, the downstream evaluation and synthesis cannot manufacture better source material.

Resilience Loop

3. Resilient Multi-Provider Inference & Fallback

Relying on a single AI provider creates an immediate single point of failure. When an agent requires inference, it evaluates an ordered priority chain of configured providers with automatic, graceful fallback.

The Inference Lifecycle

v0.4.0 Architecture
1 Configured Providers
→
2 Per-Task Health
→
3 Deterministic Selection
→
4 Provider Invocation
→
5 Fallback or Success
→
6 Result & Telemetry
  1. Configured Priority Chain: Providers are configured in preference order (e.g., Provider A → Provider B). Concrete provider instances are validated at service startup without performing premature inference calls.
  2. Per-Task Health Observation: Before candidate selection, the agent probes configured providers concurrently with bounded timeouts. Probes return authentic point-in-time snapshots; failed or timed-out probes yield no snapshot.
  3. Deterministic Provider Selection: Verified healthy providers are ranked first in configured priority order. Providers that are unavailable or unknown are excluded from selection.
  4. Provider Invocation: The agent invokes the top candidate to generate completions or synthesize research findings. Latency is measured strictly around the provider network call.
  5. Success or Eligible Fallback: If the model call succeeds, the result is processed immediately. If a fallback-eligible provider failure occurs and another candidate is available, execution advances to the next provider in the fallback loop.
  6. Result & Operational Telemetry: Each invocation emits exactly one attempt telemetry record over Redis, and provider transitions publish fallback events. If all candidates are exhausted or an ineligible error occurs, execution terminates with a clean error.
💡 Core Architectural Truths
  • Configured ≠ Healthy. Static presence in configuration proves only that credentials or options were provided at startup. It does not prove the remote endpoint is currently reachable.
  • Selected ≠ Successful. Ranking as the top candidate does not guarantee inference will succeed. Live network drops and upstream capacity spikes can happen at any moment.
  • Unknown ≠ Healthy. If a health probe times out or fails, health remains unknown. The platform never assumes or fabricates a healthy state.

Transparency

4. Observable AI in Practice

Every transition is visible. Instead of wondering why a task was routed to an agent, which inference provider was used, or why a candidate was skipped, the platform records structured decision and execution context.

Routing Decisions

Every task dispatch logs the resolved capability, the candidate pool evaluated, candidate availability states, and the deterministic reason for selection.

Heartbeat Liveness

Agents emit periodic heartbeat signals. Stale agents (>30s) and offline agents (>90s) are automatically disqualified from work without restarting services.

Inference Attempt Telemetry

Every provider invocation emits a structured telemetry record capturing provider name, model, invocation latency in milliseconds, attempt index, and sanitized status.

Fallback Transition Events

When execution switches from a failed provider to a backup candidate, a structured fallback event captures the transition, displayed live in the Prototype Console activity timeline.

Task Result Metadata

Successful task results display formatted markdown, attributed citation links, and execution metadata showing the successful provider, model (when known), latency, and attempt number.

State & Event Streams

Operational events stream asynchronously over Redis Streams and Hashes for live browser observability without blocking or slowing task execution.
