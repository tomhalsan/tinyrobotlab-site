How Tiny Robot Works

Tiny Agent Lab is the current project within Tiny Robot Lab. For capability-routed work, it assesses the task, checks for a capable ready agent, and dispatches to the agent's advertised target. An optional advisor can resolve ambiguous assessments; research and inference add their own evaluation and fallback stages.

1. Capability-Driven Task Dispatch

The capability-driven path routes by advertised capability and current availability, rather than by a fixed worker identity.

  1. Prompt submission

    An operator submits a natural-language task through the Prototype Console or HTTP API.

  2. Capability assessment

    The deterministic router proposes general or research and records its assessment signals. If the assessment is ambiguous, a configured advisor may recommend the final capability.

  3. Candidate discovery

    The orchestrator finds registered agents that advertise the required capability.

  4. Availability evaluation

    Heartbeat age and execution state distinguish ready, busy, stale, and offline agents. Only eligible candidates proceed.

  5. Deterministic selection

    Default candidate ordering is deterministic by agent ID. The routing decision records the selected candidate and its rationale.

  6. Target dispatch

    The capability-driven path sends the task to the selected agent's advertised target. A static-enqueue path remains for legacy non-dynamic configuration and backward-compatible tests.

  7. Execution and result

    The agent processes the task and returns its output. Operational events carry state changes and related runtime details.

2. Grounded Research Execution Pipeline

With the Tavily-backed executor, search results are normalized into candidate evidence and evaluated before synthesis. Synthesis runs when an inference provider is configured, and the task result retains evaluated source records.

  1. Web retrieval

    A configured Tavily executor sends the prompt to Tavily Search, directly or through its MCP adapter. Results may include URLs, titles, snippets, relevance scores, and publication dates.

  2. Candidate normalization

    The result processor maps each item to candidate evidence, preserving its URL, title, snippet, provider score, and publication date when supplied.

  3. Evidence evaluation

    The evaluator filters invalid or duplicate URLs, promotional material, and short snippets. It ranks the remaining items using domain authority, query-keyword relevance, cross-domain keyword overlap, provider score, and explicit publication-date recency.

  4. Grounded synthesis

    When an inference provider is configured, the Research Agent passes formatted evidence to synthesis. A Tavily-supplied summary is included when present; the inference prompt asks the model to rely on supplied material and cite its URLs.

  5. Attributed result

    When synthesis runs, the result retains evaluated source records alongside the answer. The prompt requests a concise Sources section with the available URLs.

Caveat: evaluated evidence is not factual truth
  • Evaluated evidence is not verified proof. EvidenceEvaluator filters and ranks candidates using heuristics; it does not establish factual accuracy.
  • Cross-domain keyword overlap is not corroboration. Separate sites may repeat the same source or phrasing.
  • Retrieval quality is bounded by the provider. If the upstream retrieval API returns low-quality or irrelevant candidates, the downstream evaluation and synthesis cannot manufacture better source material.

3. Resilient Multi-Provider Inference & Fallback

Provider configuration, live health, candidate selection, and invocation success are distinct runtime facts.

  1. Configured providers

    Provider adapters are mapped by name, and a configured preference order determines their relative priority.

  2. Per-task health probes

    Before selection, configured providers are probed concurrently with bounded timeouts. A failed or timed-out probe yields no health snapshot.

  3. Provider selection

    Healthy providers rank ahead of degraded providers; a degraded provider can still be selected if no healthy one is available. Rate-limited, quota-exhausted, unavailable, and unobserved providers are excluded.

  4. Provider invocation

    The selected adapter performs the inference call. The recorded latency surrounds the provider call, not only its network request.

  5. Eligible fallback

    Only fallback-eligible errors advance execution to the next candidate. Other errors, or exhaustion of the candidate list, end the attempt with an error.

  6. Result and telemetry

    The coordinator constructs telemetry for each provider attempt and a transition event when it falls back. Event delivery is best-effort.

Engineering axiom
  • Configured != Healthy. Configuration sets provider options and preference; it does not establish current health.
  • Selected != Successful. A provider can be selected and still fail when invoked.
  • Unknown != Healthy. A failed probe provides no snapshot, so the provider is not assumed to be healthy.

4. Observable AI in Practice

Routing records, task results, and operational events expose concrete parts of each run.

Runtime signals and the evidence they expose
Signal Recorded or displayed evidence
Routing decision The assessed capability, selected agent and dispatch target, and the decision rationale.
Agent availability Heartbeat age and execution state inform ready, busy, stale, and offline status. Only ready agents are eligible; default stale and offline thresholds are 30 and 90 seconds, and are configurable.
Inference attempt Provider, attempt index, latency, and status; model and token fields are optional.
Fallback transition Failed and next provider, reason, and attempt index. The Prototype Console displays transition events in its activity timeline.
Task result The Console formats the output and displays provider, model when present, latency, and attempt metadata when telemetry is available.
Operational events AgentEvent records are published to the Redis stream agent.events and can carry state, routing decisions, fallback transitions, and inference telemetry.
